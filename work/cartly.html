What it does

A grocery marketplace with three roles — customer, merchant, admin. The customer-facing hook is the part worth talking about: pick a recipe, set how many people you are cooking for, and get a cart. Not a shopping list. An actual cart, grouped by merchant, with real package quantities and prices.

That sounds like a small feature and is where all the difficulty lives. Recipes are written in grams and millilitres; shops sell 500 g bags and 1 L bottles. Four ingredients might be cheapest across three different merchants, which means three deliveries. And the answer has to be the same every time, because a cart that reshuffles between page loads destroys trust immediately.

The engine

Three lines of arithmetic:

scale_factor      = selected_servings / base_servings
scaled_quantity   = recipe_ingredient.quantity * scale_factor
required_packages = CEIL(scaled_quantity / product.package_quantity)

The CEIL is the honest part — you cannot buy 0.4 of a bag, so the cart shows what you will actually pay and flags the excess rather than quietly pretending the fractional amount is free.

Determinism through a published tie-break order

When several products satisfy an ingredient, candidates are ranked in a fixed sequence:

  1. merchants already used in this cart — fewer deliveries beats a marginally cheaper item
  2. fewest packages
  3. lowest excess quantity
  4. lowest cost
  5. highest rating
  6. lowest product ID

The last criterion is the one that makes it fully deterministic: no matter how many products tie on everything else, the ID breaks it. Same recipe and same catalogue always produce the identical cart, and because the order is documented in the README anyone can verify a given result by hand. Every edge case — ingredient with no stocked product, package larger than the whole requirement, merchant out of stock mid-build — produces an explicit warning attached to the cart instead of a silently missing line.

The framework underneath

The brief ruled out Laravel and Symfony, so the team built the layer instead: router, base controller, base model, autoloader, CSRF token handling, validator, flash messaging and a file-upload helper. Not because that is better than a framework — it plainly is not — but it does mean nobody on the team could treat request handling, routing or CSRF as magic. Every request path is code somebody in the room wrote.

All database access goes through PDO prepared statements. Sessions handle auth, passwords are hashed, mutating forms carry CSRF tokens, and payment runs through a mock gateway with its own transaction records.

My part: the merchant module and the schema

I owned the whole merchant side — dashboard, store profile, product CRUD, stock, price, package and category management, voucher creation, order management and return requests — and designed the database the rest of the application sits on.

Two schema decisions I would defend in review:

  • merchant_orders splits a customer order per merchant. One checkout can produce several fulfilments with independent statuses, delivery tracking and subtotals. Without that table, a two-merchant order has no coherent state — one half shipped and the other half cancelled has nowhere to live.
  • order_items stores a product snapshot, not just a foreign key. Name, unit price and quantity are copied at purchase time. When a merchant later edits a price, historical orders and receipts stay truthful.

How the team worked

Unusually for coursework, this repo has a real process attached — and it is the thing that transferred most directly to working at UniPin a few months later.

  • 181 commits across four contributors, branches linked to tickets
  • GitHub Actions for PHP linting and pull-request checks
  • An RFC template for changes that touched shared code, and a two-reviewer rule
  • 12 PHPUnit test files
  • 2,861 lines of engineering documentation — a 1,200-line specification, an architecture document, a contributing guide, a changelog and an RFC workflow description

Limitations

  • Payment is a mock gateway. No real PSP integration, no PCI scope.
  • Test coverage exists but is thin relative to 10,400 lines — the engine and the schema are covered, the views largely are not.
  • Product matching relies on merchants classifying products against a shared ingredient list. A real deployment would need fuzzy matching or a curated catalogue, because merchant-entered data will not be that tidy.
  • No caching layer; the cart builder queries per ingredient, which is fine at coursework scale and would not be at real scale.
